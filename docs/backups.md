# Резервные копии

Каждую ночь сохраняются две вещи: дамп базы данных и архив загруженных
файлов. База — это заявки, прайс, тексты, работы и учётки админки; файлы —
фотографии работ и картинки, загруженные через `/admin/media`. Без второго
восстановленная база будет ссылаться на несуществующие изображения.

## Установка на сервере

```bash
cd /path/to/birkityt
bash scripts/install-cron.sh          # ежедневно в 03:30
```

Другое расписание — первым аргументом в формате cron:

```bash
bash scripts/install-cron.sh "0 4 * * *"
```

Скрипт идемпотентный: повторный запуск заменяет прежнюю строку, а не плодит
дубликаты. Проверьте, что служба cron вообще работает:

```bash
systemctl status cron
```

## Что и куда пишется

| | |
|---|---|
| Каталог | `BACKUP_DIR` из `.env`, по умолчанию `./backups` |
| Дамп базы | `db-ГГГГММДД-ЧЧММСС.sql.gz` |
| Файлы | `uploads-ГГГГММДД-ЧЧММСС.tar.gz` |
| Хранение | `BACKUP_KEEP_DAYS` дней, по умолчанию 14 |
| Журнал | `backups/backup.log` |

Каталог `backups/` в `.gitignore` — дампы содержат персональные данные из
заявок и хеши паролей, в репозиторий им нельзя.

## Проверка

Запустить вручную и посмотреть, что получилось:

```bash
bash scripts/backup.sh
ls -lh backups/
```

Скрипт падает с ненулевым кодом и пишет в журнал, если контейнеры не
запущены, `pg_dump` выдал ошибку или дамп получился подозрительно маленьким
(меньше 1 КБ — обычно это признак того, что вместо данных записался текст
ошибки).

Если в `.env` заполнены `MAX_BOT_TOKEN` и `MAX_CHAT_ID` (те же, что для
уведомлений о заявках — см. [notifications.md](notifications.md)), то при любой
ошибке придёт сообщение в MAX, а по понедельникам — короткая сводка
«всё в порядке». Ежедневных сообщений нет
намеренно: канал, который пишет каждый день одно и то же, перестают читать.

## Восстановление

```bash
bash scripts/restore.sh backups/db-20260824-033000.sql.gz \
                        backups/uploads-20260824-033000.tar.gz
```

Скрипт останавливает веб-приложение, разворачивает дамп, распаковывает файлы и
запускает всё обратно. Он спросит подтверждение — текущее содержимое базы будет
заменено.

Второй аргумент необязателен: без него восстанавливается только база.

**Проверьте восстановление хотя бы один раз**, пока ничего не горит — лучше на
отдельной машине или в отдельном каталоге. Копия, из которой никогда не
разворачивались, копией не считается: типовая история — восстановление
впервые запускают в аварии и там же узнают, что дампы месяц писались пустыми.

## Чего эта схема не делает

Копии лежат **на том же сервере**, что и сайт. От испорченной миграции,
случайного `DELETE` и неудачного деплоя это защищает, а от потери самого
сервера, шифровальщика или удаления аккаунта у хостера — нет.

Минимальное улучшение — забирать копии на другую машину. Например, с рабочего
компьютера по расписанию:

```bash
rsync -avz --delete user@birkityt.ru:/path/to/birkityt/backups/ ~/birkityt-backups/
```

Либо настроить выгрузку в S3-совместимое хранилище (Yandex Object Storage,
Selectel) через `rclone` — тогда достаточно добавить одну строку в конец
`scripts/backup.sh`.
